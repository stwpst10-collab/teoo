## 관계와 상태

사업은 고객을 대상으로 한다. 고객은 문제를 겪는다고 가정한다. 제품은 문제를 해결한다고 가정한다. 검증 계획은 가설을 시험한다. 근거 문서는 가설의 출처 또는 실제 검증 결과를 제공한다.

관계는 본문의 설명과 위키링크로 함께 기록한다. 단순 링크를 인과관계나 검증의 증명으로 보지 않는다.

산출물은 `OUT` ID로 식별하고 `output_kind`로 시뮬레이션모델링(simulation-model)과 프로토타입시안(prototype-concept)을 구분한다. 산출물 → 참조 결정, 산출물 → 반영 연구, 산출물 → 사용 가정의 관계를 설명 노트에 명시한다. 확정 여부는 별도 `status`로 표시한다.
`status`로 가설·출처·검증 결과를 구별한다. 결과를 추가할 때 날짜, 방법, 관측 결과, 출처를 기록한다. 목표 수치를 실제 달성값으로 바꾸어 읽지 않는다.

## 자료 관리

새 사업 지식은 이 vault에서 관리한다. 원본 자료는 출처 링크를 유지하고, 복사한 자료에는 복사 날짜를 표시한다. 린캔버스와 시뮬레이션은 서로 다른 버전의 자료로 취급한다.


## 2026-10-28 추가 관리 항목

- `decision`: 현재 적용할 팀 결정. 근거와 적용 범위, 이전 가설과의 관계를 기록한다.
- `milestone`: 단계별 상태와 승인 여부. 발표 예정과 사업화 확정을 구분한다.
- `research-queue`: 해결해야 할 질문, 기존 근거, 필요한 증거, 우선순위.
- `workflow` / `template`: 운영 방식과 기록 양식.

회의 결론과 업체 발언은 서로 다르다. 한 문서에 함께 있어도 각 주장 수준에서 확정·미확인을 구분한다. 최신 날짜의 제안이 기존 결정을 자동 대체하지 않는다.
상세 운영은 [[리서치-운영|리서치 운영 방식]]을 따른다.

## 공동 저장소의 식별과 검토

`id`는 속성에 보관하는 고정 식별자다. 파일명은 한글 주제 중심으로 쓰며 ID를 앞에 붙이지 않는다. 조사에는 `type: research`를 사용한다. Ovira 조사도 리서치로 재분류했으며 원문 목록·본문·기존 근거 수준은 보존했다. 상세 규칙은 [파일명과 메타데이터](파일명과-메타데이터.md), 제출 흐름은 [참여 안내](../CONTRIBUTING.md)를 따른다. `review`는 동료 검토 여부, `status`는 주장·문서의 상태다.
