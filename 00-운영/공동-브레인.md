# 하나의 브레인처럼 일하는 방법

핵심은 모든 파일을 합치는 것보다 **팀이 지금 무엇을 믿고, 왜 믿고, 무엇을 아직 모르는지**를 같은 기준으로 관리하는 것이다. 다음은 운영 제안이며 담당자·주기 합의는 아직 없다.

## 판단이 쌓이는 흐름

질문 → 출처 → 리서치의 주장과 반대 근거 → 공통 지식 갱신 → 필요한 팀 결정 → 실험 → 새 관측 결과 → 질문 갱신.

README는 입구, 10-지식은 현재 설명, 20-리서치는 추론 과정, 30-근거는 원문, 40-결정은 선택의 기록이다. 하나의 긴 요약 문서에 모두 복사하지 않는다. 현재 판단에서 원문까지 따라갈 수 있어야 한다.

## 지금 적용할 운영안

1. 질문 목록을 공동 백로그로 쓴다. 조사를 시작하기 전에 Q 번호·담당자·기한·기대 산출물을 GitHub 이슈에 적어 중복 조사를 줄인다. 이슈를 아직 만들지 않았으며 같은 항목을 여러 파일에 중복 관리하지 않는다.
2. 팀원은 근거를 수집하고 자신의 해석을 작성한다. 자신에게 유리한 자료만 모으지 않고 반례와 적용 한계를 같은 파일에 남긴다.
3. 사용자가 통합 편집자 역할을 맡는다. PR마다 “이 근거로 현재 설명이 어떻게 달라지는가?”를 확인해 해당 공통 노트를 수정하거나 변경 없음의 이유를 기록한다.
4. 결정권자만 제품 범위·가격 가정·검증 목표를 확정한다. 변경 시 새 결정에서 이전 결정을 연결한다. 과거 결정은 삭제하지 않는다.
5. 주 1회 짧은 판단 회의를 제안한다. 새 근거, 서로 충돌하는 주장, 바뀐 판단, 다음 검증만 다룬다. 회의록으로 결정을 대신하지 말고 결정 노트를 연결한다.

## 주장 충돌을 다루는 작은 표

각 리서치 본문에 다음을 적는다. 별도 데이터베이스를 먼저 만들 필요는 없다.

| 주장 | 지지 근거 | 반대 근거/한계 | 적용 조건 | 영향받는 지식·결정 | 현재 판단 |
|---|---|---|---|---|---|
| 조사에서 다룬 한 문장 | 원문 위치·날짜 | 반례 또는 미확인 | 대상·사양·수량 등 | 고정 ID와 링크 | 확인/반박/유보 |

예를 들어 “패치가 재구매를 만든다”는 판매 가설이다. 경쟁사가 패치를 팔았다는 관측과 우리 고객이 반복 구매했다는 결과는 다르다. 둘을 같은 확실성으로 저장하지 않는다.

## AI도 같은 기억을 읽도록

각 팀원은 최신 중앙 main을 받은 뒤 AI에게 AGENTS.md와 질문 관련 노트를 읽게 한다. 같은 질문·현재 결정·기준 커밋에서 출발한다. AI가 새 출처와 영향을 받은 기존 노트를 함께 제안하고, 사람이 검토한다. 채팅 기억이나 다른 팀원의 개인 메모는 자동 공유되지 않는다.

요청 예시: “AGENTS.md를 따르고 Q11을 조사해. 관련 리서치와 현재 결정을 먼저 읽고, 새 근거·반대 근거·ALT/ASM/SOL 노트 변경안을 PR에 포함할 수 있게 작성해. 기존 결정은 승인 없이 확정하지 마.”

## 나중에 추가할 자동화

현재 폴더에 [PR 현황판](../05-협업/PR-현황.md)과 [조회·이력 운영 안내](../05-협업/README.md)를 추가했다. 같은 사용자 저장소의 작업 브랜치를 공유하는 방식이며 별도 fork가 기본은 아니다. 원격 미연결 상태라 자동 조회는 아직 가동하지 않았다.

- 첫 단계는 이번에 추가한 ID·링크·메타데이터·충돌 표식 CI다. 사실의 참/거짓은 자동 판단하지 않는다.
- 자료가 늘면 날짜가 오래된 가격·사양·규정의 재확인 목록을 만든다. 모든 자료를 무조건 최신으로 덮어쓰지 않는다.
- 검색이 실제로 어려워질 때 임베딩 검색이나 그래프 DB를 검토한다. 원문·ID·관계·검토 이력이 먼저 쌓이면 나중에 옮기기 쉽다.
- 자동 요약은 매번 출처와 기준 커밋을 붙이고, 공통 지식 갱신은 PR로 검토한다. AI가 판단을 조용히 바꾸게 하지 않는다.
