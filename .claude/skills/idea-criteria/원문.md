# 사업 아이디어 시뮬레이션

새 사업 아이디어(이름 한 줄이어도 됨)를 받아, 사내 사업 제안 수준의 검토 패키지를 만든다. 결과물은 한국어.

## 항상 지키는 규칙
1. **리서치 기반**: 모든 수치·주장은 웹 검색으로 확인하고 출처를 단다. 기억으로 숫자를 채우지 않는다.
2. **백데이터는 하단에**: 장표마다 맨 아래 `출처 [번호]` 줄, 덱 끝에 참고 자료 장표(장당 8개, 번호 연속, 중복 번호 금지).
3. **근거 없는 숫자는 공란**: '공란' + 채우는 방법(설문 문항, 실측, 견적처)을 함께 적는다. 신뢰도가 낮은 출처는 '신뢰도 낮음', 근거 없는 판단은 '추론', 검증 전 가정은 '가설'로 표기. 출처끼리 수치가 크게 다르면 범위와 차이를 그대로 보여준다.
4. **전문가 관점**: 각 검토는 분야별 전문가(도메인 과학, 엔지니어링, 디바이스, 안전·의학, 법률, 공장·물류, MD·구독, 재무·투자, 계열사 전략 등 아이템에 맞게) 단계의 디깅으로. 표 형식: 전문가 | 진단/지적 | 대안 | 근거 | 실현가능성(상·중·하).
5. **피드백은 제품에 엎는다**: 지적은 반드시 사양·운영 변경으로 반영하고 '반영/실측 필요/필드 검증/가설' 상태를 표시.
6. **대안은 실현가능성 기준**으로 고르고, 정직한 범위(되는 것/안 되는 것)를 먼저 밝힌다.
7. **과장·법률 리스크 표현 금지**: 효능·의료·퇴치 연상 표현은 유권해석 전엔 쓰지 않는다. 표시 문구는 '기록·모니터링' 수준부터.
8. **사용자의 방향은 존중하되 리스크는 구조로 푼다**: 사용자가 원한 방향(예: '한 번에 해결')을 뒤집지 말고, 완성형 목표로 두고 출시 게이트로 단계화한다.

## 순서 (단계마다 프로젝트 MD 1개 + 장표 반영)
1. **타겟 고객**: 후보 세그먼트 순위, 거부 대상과 이유, 페인포인트 백데이터, TAM(숫자)·SAM·SOM(근거 없으면 공란).
2. **아이템 정리**: 템플릿(아이템_정리_템플릿.md) 출력 형식 0~5로 정리. 3요소(디바이스/제품 + 앱 + 반복매출), 상호의존 루프, 대체재 비교(가격 앵커 포함), 해자, 문제-솔루션 정렬. 6개 조건 ○/△/× 자체 채점.
   - **앱 단독 가치**를 반드시 설계한다: 디바이스 없이도 앱만으로 쓸모 있는 기능(판별·기록·판정·안내·지도·연결). 디바이스는 '필수'가 아니라 '자동화·정확도 업그레이드'로 둔다.
3. **전문가 심층 검토 → 재설계**: 분야별 점검표, 핵심 근거 차트, 재설계안(기존 vs 변경), 고도화 리스크 점검, 최종 사양표, 대안(더 센 방법) 검토와 하이브리드 권장안.
4. **유사 제품·경쟁사·빈자리**: 경쟁 지도(범주 | 사례 | 갖춘 것 | 없는 것 | 우리), 빈자리 명시.
   - 재무 관점: 세그먼트별 시장 규모·성장·판정·수치 신뢰도, 경쟁사 매출·성장·수익성·강점·위협, 이익의 원천·밸류 레버·출구 사례.
   - **'왜 아무도 안 했나'**: 기존 강자가 이 제품을 안 만드는 이유를 기술 난이도와 경제성(그들의 사업모델 기준)으로 나눠 판정. 결론에서 우리 수익모델이 그들과 어떻게 달라야 하는지 적는다.
5. **비수기·사용성 공백 대응**: 매출이 줄어드는 경로 진단 → 축별 대응(쓸 이유 / 끊기지 않는 구독 / 계절 없는 고객) → 전문가별 대안표 → 실행 순서와 KPI(목표 없으면 공란).
   - 평상시 기능 추가 제안(예: 디퓨저·인테리어)은 핵심 기능과의 충돌, 타깃 안전, 규제 세 가지로 판정한다.
6. **사업 모델·확장**: 수익 사다리(무료 앱 → 구매 → 구독 → 부가 매출).
   - 경로표: B2C(시작점) / B2B2C(밸류 레버) / B2B(선별). 'B2C만'인지 묻는 질문엔 경로표로 답한다.
   - B2C 안의 확장 4축: 고객·문제·수익·채널 × 1·2·3단계. 확장 고객이 현재 TAM 밖이면 '별도 산정(공란)'으로 표시한다.
7. **모회사·계열사 당위성** (해당 시): 전략 적합, 자산 재활용, 시장 타이밍, 리스크. 1단계는 주관 1 + 협력 1로 압축하고, 나머지 계열사는 단계를 표시한다.
8. **레드팀**: 심사위원 관점 재채점, 핵심 리스크 5~6개와 전문가 보완, **출시 게이트**(검증 전 요소는 게이트 통과 시에만 1단계 탑재, 미통과 시 축소 버전).
9. **흐름 정리·충돌 점검**: 덱 전체를 다시 읽고 아래 '충돌 점검 목록'으로 고친다. 바꾼 장표 목록을 보고.
10. **로드맵·다음 90일**: 각 할 일이 어느 게이트를 여는지 표시.
11. **린캔버스**: 아래 '린캔버스 작성법' 참조.

## 충돌 점검 목록
- 헤드라인('한 번에' 같은 약속) ↔ 범위 표(되는 것/안 되는 것)
- 1단계 구성 ↔ 출시 게이트 ↔ 로드맵 ↔ 사양표 ↔ 사용 방법 장표
- 채널·계열사의 단계 표기가 모든 장표에서 같은가
- 구독 플랜 이름과 정의(라이트·기본·연간)가 같은가
- B2B 진입 시점이 겨울 대응·사업 모델·확장·계열사 장표에서 같은가
- 앱 화면 예시에 게이트 전 기능이 들어가 있지 않은가
- 1단계 무전자부품 원칙과 어긋나는 기능(알림·통신·센서)이 1단계에 들어가 있지 않은가
- 출처 번호 중복, 참고 자료 누락

## 린캔버스 작성법
- 채우는 순서: ②고객 → ①문제 → ④해결책 → ③가치 제안 → ⑥수익 → ⑧채널 → ⑨핵심 지표 → ⑦비용 → ⑤경쟁 우위.
- 문제는 3개 이하로, 시간·비용 손실을 포함한다.
- 고객은 상황·역할로 좁힌다.
- 가치 제안은 대안 대비 한 문장.
- 해결책은 문제와 1:1로 맞춘다.
- 경쟁 우위는 '돈으로 살 수 없는 것'만 쓰고, 없으면 "아직 없음".
- 수익은 초기 가격 가설을 쓰고, 근거가 없으면 공란 + 확정 방법.
- 비용은 마진식으로 쓴다.
- 채널은 처음 고객 수십~수백 명을 데려올 직접 경로.
- 지표는 행동·전환 지표로 쓴다(누적 방문 같은 허영 지표 금지).
- 별첨: 핵심 컨셉, 첫 번째 고객, TAM·SAM·SOM, 기존 대안.
- 출력: 사용자가 준 양식 이미지 레이아웃의 HTML 페이지로 게시하고, 제출용 PDF와 md를 함께 전달한다. 팀명·팀원 이름은 모르면 비워 둔다.

## 산출물 방식
- 장표: Slides 타입 덱 하나에 섹션별로 누적.
  - 순서: 고객 문제 → 빈자리 → 솔루션(앱 → 키트 → 완성형) → 시너지·해자 → 전문가 재설계 → 레드팀·게이트·비수기 → 사업 모델·확장 → 계열사·실행 → 참고 자료.
  - 각 장표는 렌더해 넘침을 확인하고 게시한다.
- 문서: 단계별 MD를 프로젝트에 저장(`claude/<아이템>_<단계>.md`)하고, 끝에 출처 목록을 단다. 구조를 바꾸면 결정 사항 문서를 남긴다.
- 요청 시: 3×4 썸네일 PNG, 원페이지 컨셉보드 PNG, 깃허브용 단일 기록 파일.

## 시작할 때
아이디어 이름과 (있으면) 제출처·양식·마감일을 확인한다. 사용자가 단계별 확인을 원하지 않으면 1~11을 순서대로 진행하고, 단계가 끝날 때마다 한두 줄로 결과를 알린다.

## 3. 타깃 고객 발굴 프롬프트

/deep-research

지금부터 너는 고객 Pain Point를 짚어내는 고객 전문가가 될거야.

-스타트업 벤쳐 투자자
-스타트업 성공적인 브랜딩 전략가
-고객이 굉장히 뾰족해야함 (타겟 시장이 좁아도 괜찮으나, pain point의 명료성이 뚜렷하여 한눈에 이해되는 고객군이어야함)
-Pain point가 완벽히 해결되는 대체재가 없는 고객군/사용자여야함

조금 더 타겟 고객군을 제안해줘, 원하는 만큼 토큰을 사용해도 괜찮음

사람의 생애주기별 고통이 되어도 좋고
사람의 평소 행동패턴으로 인한 고통이 되어도 좋아 (고통=Pain point)
사람이 아니어도 괜찮으나 청중의 공감을 이끌어내야함

명료하게 단어로 정의된 Painpoint도 좋으나 필요하다면 새롭게 정의해도 괜찮음

단, 아이템 디바이스는 '의료기기'(효능검증) 범위에 들어가면 안됨.

한 번 더 해보자

이번에는 기존 스타트업 시장에서 트렌드로 떠오르는 키워드도 확인해 볼 것

최근 뉴스로 이슈되는 키워드가 있었는지 점검
